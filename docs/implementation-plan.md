# JB Git implementation plan

This checkpoint describes the current source tree. It separates a workflow being present from full IntelliJ IDEA parity so that README feature lists, implementation milestones and release claims use the same boundary.

## Status model

- **Implemented**: the workflow is present and covered by the current implementation/tests.
- **Partial**: useful end-to-end behavior exists, but IDEA offers materially deeper behavior.
- **Planned**: not implemented in the current tree.
- **Out of scope**: an explicit project non-goal.

## IDEA behavior baseline

The parity baseline comes from current JetBrains documentation and the public IntelliJ Community source layout:

- [Commit and push changes](https://www.jetbrains.com/help/idea/commit-and-push-changes.html) — Staging Area, partial commit, per-chunk/per-line selection and Changelist workflows.
- [Resolve Git conflicts](https://www.jetbrains.com/help/idea/resolve-conflicts.html) — Base-aware three-pane merge, non-conflicting/simple-conflict actions and result review.
- [Merge, rebase, or cherry-pick changes](https://www.jetbrains.com/help/idea/apply-changes-from-one-branch-to-another.html) — branch integration and interactive rebase.
- [Investigate changes](https://www.jetbrains.com/help/idea/investigate-changes.html) — Log, file history and editor-gutter Blame annotations.
- [Changelist settings](https://www.jetbrains.com/help/idea/settings-version-control-changelist-conflicts.html) — same-file partial-change ownership and inactive-Changelist conflict policies.
- `plugins/git4idea/backend/src/commands` and `repo` — Git command execution and repository state.
- `plugins/git4idea/backend/src/index`, `status`, `branch`, `rebase`, `merge` and `stash` — Index, status and operation workflows.
- `platform/vcs-impl` — Changelists, Shelf, Patch, Diff and Merge infrastructure.
- `platform/vcs-log` — commit graph and log data layers.
- `plugins/git4idea/tests` — independent parity-test inventory.

The implementation is clean-room TypeScript. Any future source reuse requires per-file license review and attribution.

## Capability checkpoint

| IDEA capability | Status | Current implementation and remaining boundary |
| --- | --- | --- |
| HEAD / Index / Working Tree model | Implemented | The UI keeps `HEAD → Index` and `Index → Working Tree` separate. It supports file Diff and text-Hunk stage/unstage, with stale-Hunk identity checks before applying a patch. |
| Two commit sources | Implemented | **Staging area (Index)** commits exactly the staged snapshot. **Selected files (complete contents)** uses an isolated temporary Index and therefore does not destroy the real Index if staging, hooks or commit fail. Selected-Changelist commit uses the same complete-path model. The commit form carries IDEA's message conveniences: checking **Amend** fills the box with the commit being amended (restoring the typed draft on uncheck, and ignoring a reply that arrives after the box was unchecked again), and Commit Message History offers back the last 25 messages that were actually committed, per repository, newest first, with re-use moving an entry to the front. Unversioned files are listed but start unchecked, because a tracked change is work the user did while an untracked path is routinely a build artefact — pre-checking them once made Commit stage 2,475 editor-cache files. The Author field is `GitCommitOptions.author` → `--author=`, bounded to one line at the protocol boundary, completed from `recentAuthors` (cached until HEAD moves) and cleared after the commit; `commit.template` is read through `git config --get --path` (30-second cache), pre-fills an empty box, and makes the commit run with `--cleanup=strip` so template comments go the way Git's editor sends them. |
| Host-side localization | Partial | Every command's native dialogs, notifications, Quick Picks and progress titles go through `vscode.l10n` with a zh-cn bundle (400+ entries); tests keep every used key translated, every bundle entry used, every placeholder intact, and forbid deciding anything by sniffing words out of a translated label. Remaining: input-validation and rebase-plan messages (pure modules with no VS Code import, so the webview and unit tests can load them), and the log panel's branch context-menu items that concatenate branch names. |
| Changelists | Partial | Create, describe, activate, delete and move whole files; preserve assignments through renames; commit a selected Changelist. Per-Hunk ownership inside one file is implemented: a file has one home Changelist and individual hunks can be claimed away from it, which is what makes an unrelated fix separable from the feature work around it. A hunk is named by a digest of the lines it adds and removes plus its ordinal among identical ones, because line numbers and surrounding context move for reasons that have nothing to do with the change; claims follow a rename and are dropped once the change they name is gone. The commit distinguishes the two cases that cannot share one set of names — the home list commits everything the others did not claim, including a hunk that appeared since, while a claiming list commits only what it claimed — and applies the resulting patch with `git apply --cached` into the same isolated index a selected-path commit already uses, so the other lists' hunks stay in the working tree and a failure leaves the real index untouched. A stale claim is refused rather than silently committing less than the user reviewed. Overlapping line-level ownership within a single hunk, task context and inactive-Changelist conflict handling remain planned. |
| Rollback and recovery | Implemented | Tracked-file Rollback first persists a recovery Shelf. Untracked deletion goes through the operating-system Trash. Individual conflicted-file rollback is blocked so one conflict side is not silently lost. Ignore for an unversioned file (`ignoreRules`) offers the exact file, its directory or its extension, anchored and escaped, appended once to the top-level `.gitignore` or to `info/exclude` in the common Git directory so linked worktrees share it. |
| Shelf, Stash and Patch | Partial | Shelf create/apply/delete, Stash create/apply/pop/delete, commit-patch export and patch import are present. Recovery uses persisted Shelf patches and stash OIDs; arbitrary local-change patch construction and IDEA's broader Unshelve targeting/options remain gaps. |
| Smart Checkout | Implemented | Dirty checkout stashes tracked, staged and untracked changes, identifies the temporary stash by immutable OID, checks out, and restores Working Tree plus Index. Failed/conflicting recovery keeps the stash. The Branches popup is a `createQuickPick` with item buttons: Recent from `reflogSubjects` through `recentBranchesFromReflog` (both ends of each checkout, existing local branches only), Favorites in `FavoriteBranches` (workspace state, keyed `kind:name`, pruned against the live branch list), and Update (`updateBranch`: `git fetch <remote> <merge>:refs/heads/<name>`, fast-forward only, refused for the checked-out branch which is pulled instead). |
| Push preview and recovery | Implemented | Fetch-before-preview, an exact fully-qualified source/destination refspec, outgoing commit list, initial upstream, configurable destination-branch protection, Force with Lease only, and checked-out existing-upstream non-fast-forward recovery through Pull with Rebase/Merge followed by a new preview. IDEA's richer multi-repository Push dialog and background incoming/outgoing model are not claimed. |
| Log and object IDs | Partial | Graph, filters, branch comparison, progressive 300-commit loading, virtualization after 500 entries and a 5,000-entry cap are present. Full 40-character SHA-1 and 64-character SHA-256 IDs pass through UI validation. Local branch rows carry IDEA's incoming/outgoing markers, parsed from `%(upstream:track)` which the branch listing already collected: ↓n incoming, ↑n outgoing, and `gone` when the upstream ref was deleted, with the existing refs fingerprint repainting the column when a fetch changes the counts. The log search field works like IDEA's: typing filters the loaded window, Enter runs `git log --fixed-strings --regexp-ignore-case --grep` over the whole walk through the same read path as every other log view, and a hex entry re-roots the log at that commit — go-to-hash for commits outside the loaded window. Clearing the box (including its native ✕) ends the search, revealing a commit clears a search that could exclude it, and the text is bounded and single-line at the protocol boundary because it lands in a command argument. Persistent indexing remains planned. The commit list multi-selects (Ctrl/Cmd toggle, Shift ranges by click or arrow); the selection lives in the Webview but every action re-derives its order from the host's own log — `oldestFirst` in the protocol module — so batch Cherry-Pick applies oldest-first regardless of click order and stops on the first failure naming how far it got, and Compare Versions diffs exactly two commits old → new through the existing `diffRefs`. Drop Commit and Squash Selected rewrite history from the log through pure plan builders (`dropPlan`, `squashPlan`) lowered onto the interactive-rebase machinery: candidates come from the same loader as the sequence editor with the same refusals, a non-adjacent squash names the implied reorder before confirming, and the stash choreography matches the editor (parked only after consent, kept on a conflict stop, restored on success). Edit Commit Message (`rewordPlan`) and Undo Commit complete IDEA's per-commit menu: the message is edited inline in the details pane, HEAD is amended with `--amend --only` so staged work is not swept in, an older commit goes through the same rebase plans, and Undo is a soft reset guarded by a HEAD comparison inside the mutex, refused for merges and root commits, with a pushed commit named in the confirmation. Reset offers Soft/Mixed/Hard/Keep. The branch menu has Checkout and Rebase onto Current, run as one exclusive stash → checkout → rebase → restore flow (`SmartCheckoutOptions.afterCheckout`), which keeps the stash when the rebase stops. Fixup… (`fixupPlan`) commits the Index as `--fixup=<target>` and folds it in through the same plan machinery, or amends when the target is HEAD; the linear-history check runs before the fixup commit is made. |
| Conflict resolution | Partial | The three-pane editor renders the merge the way IDEA does: the result is marker-free text whose conflicts live on as coloured ranges (the mergeRegions model, injected into the Webview so one tested implementation serves both sides), the strips between panes draw per-change connectors, and each change carries a pair of gutter actions on both strips — an arrow applies that side, and the outer slot holds `×` while the change is open and a revert arrow once it is settled, so no change is ever left with an empty gutter. Applying the second side keeps both; revert undoes one change without disturbing any other decision. Unresolved/applied/hand-edited/ignored states are coloured red/green/blue/grey, a remaining-changes counter gates the staged Apply, an action scrolls the change it moved on to back into view, a marker strip shows every change in the file, the syntax layer paints only the visible slice (a keystroke on a 3,000-line merge cost ~148ms before and now stays inside a frame), Escape aborts, every decision or typing burst is one model-level undo step (textarea history dies on programmatic assignment), zero-length conflicts render as deletion marks, and the wheel scrolls across the strips, per-block choices answer to keys 1/2/3 while focus is outside the editable result, and per-block and whole-file choices, navigation (including F7), external-change detection and marker-form drafts remain. Rebase stage labels correctly say **Rebase Target** and **Replayed Commit** using replay metadata. The merge is now replayed in `diff3` on copies of the three stages, so every conflict carries its base: **Resolve Simple Conflicts** settles the blocks with one possible outcome (both sides made the same edit, only one side changed the base, or the two differ only in whitespace) and stages a file only once nothing is left to decide. A file whose own content holds conflict markers is refused rather than framed by guesswork. The base is now displayed per block: a **Base** toggle floats IDEA's "previous contents" frame for the change you are on, above the change when it fits and below it when it does not, hidden outright once that change scrolls away rather than parked at an edge where it would read as belonging to another line. Pairing a replayed base to a working-tree conflict is refused unless the replay produced the same conflicts, in the same order, with the same two sides — Git's merge strategy can match lines the plain three-way replay does not, and a block labelled with another block's history would be worse than no base — so the toggle is simply unavailable where that check fails. Compare contents is implemented as a Quick Pick over all six pairings of Left/Base/Result/Right, opening a native read-only diff rather than a fourth surface rendered inside the Webview; the result travels with the request because it is the one version the extension host does not have, and the base pairings are withheld from an add/add conflict that has no common ancestor. Accept Yours / Accept Theirs are on the conflicted row's menu in Local Changes: `acceptConflictSide` checks out one stage and re-adds the path, or `git rm`s it when that side deleted the file, after re-checking the path is still unmerged; the sides are labelled by `conflictSideLabels`, so a rebase names Rebase Target and Replayed Commit. Still missing against IDEA: full semantic alignment. |
| Merge/Rebase/Cherry-pick/Revert/Reset | Partial | Start plus Continue/Abort/Skip operations are present, but history-editing depth remains below IDEA. The merge command carries IDEA's dialog options (`GitMergeOptions`: `--no-ff`, `--ff-only`, `--squash`, `--no-commit`, `--allow-unrelated-histories`), validated by `mergeArguments` so a combination Git rejects is refused with a sentence first. The rebase command is IDEA's dialog: Onto plus an optional From (`GitRebaseOptions.onto`, i.e. `git rebase --onto <Onto> <From>`) and `--rebase-merges`; `smartRebase.ts` gives every plain rebase (the command and the Log's Rebase onto) the stash → rebase → restore/keep handling the interactive flows already had. Interactive rebase onto a diverged branch is the dialog's Interactive option: candidates and the plan verifier both walk `--right-only --cherry-pick onto...HEAD`, the range `git rebase` itself replays, so patch-equivalent commits are left out exactly as Git leaves them out, and the editor's expectation names HEAD rather than the newest candidate. The whole editor workflow (stash offer, editor, lease, restore-or-keep) lives in `interactiveRebaseFlow.ts`, shared with Interactively Rebase from Commit. Update Project (`pullWithLocalChanges`) and plain rebases run through `runWithParkedChanges`, one implementation of the stash → operation → restore-or-keep choreography with an optional "proceed without stash" button and cancellation. |
| Interactive rebase editor | Implemented | A visual sequence editor reorders commits and applies `pick`, `reword`, `squash`, `fixup` and `drop`. Every message-changing action is lowered onto a todo Git can run unattended, so no editor is ever spawned and a paused rebase resumes from persisted message files. The plan is re-validated against the repository's own commit set before it runs. A dirty worktree is offered an explicit stash rather than refused outright: the modal states what will happen, nothing is parked until the user starts the rebase from the sequence editor, the working tree and Index are restored together afterwards, and a rebase that stops on a conflict keeps the stash instead of replaying the parked changes on top of a live conflict. Git's `rebase.autoStash` remains off — it restores unconditionally, which is the case that is hard to reason about. Untracked files no longer count as blocking, because Git replays over them and only objects to one it would overwrite. `edit` matches IDEA's stop-to-amend: the rebase parks after applying that commit — with exit code 0, so the caller reads the sequencer state instead of the exit code — the user amends or tests, and Continue resumes the rest of the plan, including a reword later in it. A squash into a run whose kept commit stops for editing is refused: the squash's amend is guarded by the leader's subject, and an edit stop invites exactly the amend that changes it. Narrower than IDEA: the starting commit must be an ancestor of HEAD, ranges containing merges are refused rather than flattened, `exec`/`break` rows are not offered, and the range is capped at 1,000 commits. |
| File History and Blame | Partial | File History and command/output Blame are implemented, including literal special-path handling. A path handed to the Log by a command is exact (`exactPath`) and followed through renames (`follow`, applied only to a literal pathspec because Git refuses `--follow` with glob magic); the typed filter stays IDEA's suffix search. Show History for Selection (`jbGit.historyForSelection`) walks `git log -L<start>,<end>:<file> --no-patch` from HEAD alone through the ordinary log reader, so paging, search, the graph and selection are unchanged; `mapLineRangeToHead` first maps the editor's lines onto HEAD through the `git diff HEAD` hunks, and the Log shows the range as a removable `Lines` chip. IDEA's per-revision file list restricted to that file is not done: the details pane shows the whole commit. Compare with Branch… / Compare with Revision… (`compareFileWithRef`) diff a ref's version of a file against the working copy; the revision picker is the file's own `--follow` history. |
| Editor-gutter Blame | Partial | Inline annotations and previous-revision traversal are implemented. `JB Git: Annotate with Git Blame` decorates each line with padded author/date/object-ID columns tinted by the commit's recency within that file, and the hover carries the subject, author, both the commit's own date and how long ago it was, and links to reveal the commit in the Log, copy the revision number and annotate the previous revision. Traversal uses Git's own `previous <commit> <path>`, so it follows a rename backwards instead of asking for today's path in yesterday's tree, and it names a boundary or first-commit line rather than opening nothing. Blame is read in `--porcelain`, which sends a commit's header block once rather than per line and costs roughly a quarter of the bytes on a large file, and an unsaved buffer is annotated through `--contents` so the annotation follows the lines being typed. Revealing a commit reports whether the Log's window actually reached it and falls back to the commit's own patch instead of quietly selecting a different one. IDEA's annotation Options are settings — `-w` to look through a reindent, `-M` to credit a block moved inside the file, `-C` to follow one copied in from another file the same commit touched — and changing one of those re-runs Git while the purely visual settings only repaint. The caret stands in for IDEA's hover: putting it on an annotated line highlights every other line of that commit, because a decoration gives an extension no pointer position. `JB Git: Annotate Revision` annotates the file as of any revision and draws that revision's own lines in bold, sharing one code path with previous-revision traversal. The hover's subject runs through the same Issue Navigation rules as the Log, so a configured issue id in it links to the tracker. Hide Revision is `GitBlameOptions.ignoreRevisions` → `--ignore-rev` (object ids only), kept per document in the controller until Show Hidden Revisions or the annotation is turned off; the hover carries both links and the hidden count. |
| Issue Navigation | Implemented | The `jbGit.issueNavigation` setting is IDEA's rule list: regular expression plus link template, `$0` the whole match and `$1`–`$9` capture groups. One pure module compiles the rules (dropping a malformed pattern, or one matching the empty string, instead of failing the feature) and splits a message into text/link segments with earlier rules winning overlapping text; the extension host uses it for the Blame hover's Markdown and the Log Webview runs the identical compiled file, injected as a sandbox global, for the details pane's subject and body. |
| Multi-root, nested repositories and Worktrees | Partial | Discovery, per-repository mutation serialization and linked-worktree metadata watching are present. External ordinary working-file changes now trigger debounced refreshes while `.git`, dependency and cache noise is ignored. Pending refreshes are retained by root/generation, and rediscovery reuses the same repository object and mutation lock when identity is unchanged. Cross-repository transactional rollback remains planned. |
| JetBrains-native UI/assets and pixel parity | Out of scope | The extension uses VS Code Panel/Webview/Diff primitives. It does not copy JetBrains source, controls, UI assets or trademarks. |

## Prioritized parity work

1. Model Changelist ownership below the hunk level, so two edits that land in one hunk can still be separated.
2. Add explicit multi-repository transaction planning, partial-failure reporting and compensating rollback where operations are reversible.
3. Add persistent large-history indexing/search and benchmark graph behavior beyond the current 5,000-commit window.
4. Widen interactive rebase towards IDEA: merge-preserving ranges and `exec`/`break` rows.
5. Bring Favorites and Recent to the Log tab's Branches pane as well, and offer Update from its branch menu.
6. Expand capability-based Git fallbacks, accessibility testing and SSH/WSL/Dev Container/remote Extension Host coverage.

## Release and signing status

Release automation is implemented, not a remaining feature. A push to `main` (unless its subject contains `[skip release]`) runs the cross-platform verification matrix, bumps the version, packages a new VSIX, commits and tags the release, and creates a GitHub Release. Marketplace upload is automatic only when `VSCE_PAT` is configured; otherwise the workflow still produces the versioned GitHub release and reports that Marketplace upload was skipped.

The project does not currently claim cryptographic VSIX/code signing or Git Commit GPG signing. Those are distinct from the implemented `Sign-off` commit option and are not prerequisites for the existing release pipeline.

## Explicit non-goals

- Pixel-perfect reproduction of IntelliJ IDEA or replacement of VS Code's native Panel/editor chrome.
- Copying JetBrains source code, UI assets, controls, product names or trademarks.
- Reimplementing Git itself; the user's configured system Git remains the source of truth.
